1Why evals aren't unit tests

  • Inputs are unbounded. Free text, not buttons and dropdowns. You can't list every case up front.
  • The model is probabilistic. Same or reworded input, different output.
  • Failures are silent. No stack trace, just a confident, well-written, wrong answer.
  • So evals are a loop, not a one-off. Simulate before launch, then update from real users.

2Benchmarks vs product evals

Model benchmarksProduct evals
TestsGeneral abilityYour task, data, tools, users
ExamplesMMLU-Pro, SWE-bench, Arena"Was the order actually cancelled?"
Use forShortlisting modelsDeciding what ships

A model that ranks low on benchmarks can win on your task. Benchmarks filter; your evals decide.

3Traces: log everything the model saw

  • User input and system prompt
  • Retrieved context
  • Every tool call and its result
  • Model replies, including sub-agents
  • Latency, tokens, model and prompt version

Store them, and build a viewer that makes one trace readable in under a minute. If reading traces is painful, nobody will do it.

4Which traces to read

MethodFinds
Random sampleUnknown unknowns. Start here.
ClusteringThemes across similar traces
OutliersMany turns, high latency, lots of tool calls

Use more signals as you learn the data, but always keep some random sampling.

5Synthetic data, carefully

  • Generate inputs only, never whole traces. Run them through the real system.
  • Start from scenarios: cancel before shipping, after shipping, unclear order, angry customer.
  • For RAG, generate a question from a document, then check retrieval finds that document.
Too clean"Cancel order #42."
Like real users"pls cancel the blue one"

6Error analysis: annotate, group, count

Annotate in plain words. One note per trace:

trace 0187
cancel_order tool returned an error,
but the agent told the user
"Your order is cancelled."

Group notes into failure categories (AI can draft them; you refine), then count:

Failure categoryTraces
False confirmation: tool failed12
Missed handoff to a human7
False confirmation: tool never called5
Wrong order picked4

Fix the biggest count first. Split a category that hides two causes.

7Should this get an eval?

  • You've seen it in traces, or can reproduce it
  • You'll iterate on it; the fix isn't obvious
  • You can say exactly what pass and fail mean
  • It matters to users or the business

Obvious bug with an obvious fix? Just fix it. Evals cost time to build and maintain.

8Pick the cheapest grader that works

GraderUse forExample
Code checkObjective rules. Fast, free, deterministic.JSON valid? Cited doc exists? cancel_order succeeded?
Classifier / decision modelClosed questions at scale. Cheap, low latency."Did the user ask for a human?"
LLM judgeJudgement and nuance"Was the reply polite, given how upset the user was?"
HumanGround truth. Doesn't scale.Labels to validate the others

Always binary: PASS / FAIL. Nobody can act on 3.9 vs 4.2 out of 5.

9LLM judge prompt template

You are checking one failure: whether a support agent claimed an order was cancelled when it wasn't.
PASS if the agent only confirms a cancellation after cancel_order succeeded, or tells the user it failed.
FAIL if it confirms a cancellation the tool calls don't support.
Examples: {3–5 labelled traces from the train set}
Trace: {trace}
Give one sentence of reasoning, then PASS or FAIL.

One judge per failure. Write criteria the way a domain expert would explain them to a new hire.

10Trust the judge before you use it

Label traces yourself (AI can propose labels; you accept or fix), then split:

Train
Dev ~40%
Test, held out
  • Train: examples inside the judge prompt.
  • Dev: compare judge vs human. Tune the prompt until they agree.
  • Test: check once at the end. Worse than dev means you overfit.
Human: passHuman: fail
Judge: pass✓Missed failure
Judge: failFalse alarm✓

11Where evals run

CI/CDOn every prompt, model or code change, against a fixed dataset
MonitoringOn sampled production traces, to catch new failures
GuardrailsIn the request path, blocking bad output. Must be fast.

12Traps

  • Generic metrics like "helpfulness 4.2/5". Not actionable.
  • Synthetic data that's too clean. Real users are messy.
  • A judge you never checked against human labels.
  • Agents rewriting prompts unreviewed. They game the evals. Review, simplify, test on unseen cases.
  • Evals for their own sake. Every eval should change a decision.

13What evals buy you

  • Prompt and model changes backed by evidence.
  • Move tasks to smaller, cheaper models: set a quality bar, keep it, cut the cost.
  • A clear "good enough to ship" line.
